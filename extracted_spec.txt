1. Executive Summary
Where Did My Money Go? is a personal finance investigation platform. It helps a user understand where money comes from, where it goes, which merchants receive it, whether spending is unusual, and which recurring payments may be reducing available money.
The first release does not connect directly to bank databases. A user downloads a statement from their bank or wallet and uploads a CSV/XLSX file, or enters transactions manually. The application validates the data, previews it, imports approved rows, categorizes transactions, and generates dashboards and reports.
The system combines deterministic rules, merchant recognition, and a machine-learning text classifier. Predictions are suggestions, not unquestionable facts. Users can correct categories, and those corrections become reviewed training examples.
The system is designed as a Flask application demonstrating routing, Jinja2 inheritance, SQLAlchemy relationships and CRUD, server-side validation, sessions, cookies, flash messages, and Post-Redirect-Get. The database design defines 40 related ORM models.
2. Problem Statement and Objectives
2.1 Problem
People often receive bank statements containing abbreviated merchant names, transaction codes and debit/credit entries. The statement lists activity but does not always explain spending patterns. Users may not know how much they spend by category, which payments repeat, or which transactions differ from their normal behavior.
2.2 Main objective
Build a secure web application that transforms uploaded or manually entered financial records into understandable, reviewable financial insights.
2.3 Specific objectives
Allow account holders to register, sign in and manage their profile.
Allow users to create financial accounts and record income, expenses and transfers.
Import bank statements from CSV/XLSX using a preview-and-confirm process.
Normalize different bank column names into one internal transaction format.
Detect likely duplicate records without silently deleting them.
Categorize transactions using merchant aliases, user rules and ML predictions.
Allow users to confirm or correct categories.
Display income, expenses, net cash flow, savings rate and category breakdowns.
Support budgets, savings goals and budget alerts.
Identify unusual transactions and recurring subscription-like payments.
Generate downloadable monthly reports.
Provide admin tools for managing global reference data and system operations while protecting private financial records.
3. Scope and Assumptions
3.1 Included in first release
CSV and XLSX statement upload; manual transaction entry.
User-owned financial accounts; no real bank credentials are collected.
Income, expense and transfer transaction types.
Categories, subcategories, merchants and aliases.
Rules-based and ML-assisted categorization with confidence and user review.
Dashboards, date filters, budgets, savings goals and alerts.
Duplicate review, anomaly review and recurring-payment detection.
Monthly report generation and in-app notifications.
Admin management of roles, reference categories, merchant aliases and import formats.
3.2 Explicitly excluded from first release
Direct access to private bank databases.
Storing bank usernames, passwords, PINs, OTPs or card security codes.
Making payments, transfers or other financial transactions on behalf of users.
Providing regulated investment, lending, tax or financial advice.
Guaranteeing that ML predictions are always correct.
3.3 Assumptions
Users have permission to upload the statements they provide.
Statement formats differ; users may need to map columns during import.
Amounts are stored as decimal values, not binary floating-point values.
Each financial account has a currency code. Currency conversion is not part of the initial release.
All timestamps are stored consistently (prefer UTC for timestamps); transaction dates are treated as local calendar dates.
SQLite is acceptable for development/demo. Production deployment should use a managed relational database and secure secret management.

9. End-to-End Workflows
9.1 Registration and sign-in
Guest opens the registration page using GET.
User submits name, email and password using POST.
Server validates required fields, email format, password policy and uniqueness.
Password is hashed using Werkzeug's password hashing utilities; plaintext is never stored.
User and default preferences are created in one database transaction.
Application flashes a success message and redirects to sign-in (Post-Redirect-Get).
On sign-in, server verifies the password hash, establishes the authenticated session and records LoginHistory.
On sign-out, session data is cleared and the user is redirected.
9.2 Create a financial account
User opens Accounts and submits account name, account type, institution label (optional), currency and opening balance.
Server validates ownership, currency code, account type and numeric amount.
FinancialAccount is created and linked to the current user.
Account list is refreshed using a redirect after POST.
9.3 Manual transaction entry
User selects an account and opens Add Transaction.
Form collects date, description, amount, direction/type, category (optional), merchant (optional) and notes.
Server confirms that the account belongs to the current user.
Server validates positive amount, valid date, currency and allowed transaction type.
Categorization service may suggest a category if none was selected.
Transaction is saved; prediction metadata is stored separately or in dedicated fields.
Application flashes success and redirects to transaction detail/list.
9.4 Statement import — key workflow
User selects an account and uploads CSV/XLSX.
Server checks file extension, MIME/signature where practical, size limit and safe filename. File is stored outside the public static folder.
Create an ImportBatch record with status Uploaded/Processing.
Parser reads file using Pandas. User selects or confirms column mappings.
Normalize column names, dates, decimal separators, debit/credit columns, signs, currency and descriptions.
Validate each row. Invalid rows become ImportError records; do not silently discard them.
Check likely duplicates using account, date, amount, normalized description and bank reference when available.
Run categorization and display a preview with row-level warnings and confidence.
User confirms import. Valid rows are inserted inside a database transaction and linked to the ImportBatch.
Update batch counts and status to Completed, CompletedWithErrors or Failed.
Delete temporary file after processing according to retention policy; keep only necessary audit metadata.
Redirect to import summary and show flash message.
9.5 Categorization workflow
Input transaction description + merchant + amount + account context                 |                 v      Normalize text (case, spaces, punctuation)                 |                 v      Merchant alias exact/normalized match?          | yes                | no          v                    v      Merchant category     User-defined/global rules?                               | yes       | no                               v           v                         Rule category   ML classifier                                             |                                      predicted class +                                      probability/confidence                                             |                          +------------------+------------------+                          |                  |                  |                       high               medium              low                          |                  |                  |                    suggest/accept     ask user to confirm   Uncategorized                          |                  |                  |                          +------------------+------------------+                                             |                                       User correction                                             |                                  Store reviewed training label
The confidence thresholds are configurable starting values, not guaranteed accuracy levels. Validate the model using a held-out dataset and choose thresholds based on precision, recall and the cost of incorrect categorization. A transaction with no informative description cannot be reliably categorized by ML.
9.6 Dashboard workflow
User chooses a date range and optionally an account.
Backend queries only that user's transactions and excludes cancelled/void records according to business rules.
Income total = sum of income transactions in range.
Expense total = sum of expense transactions in range.
Net cash flow = income minus expenses. Transfers are excluded from income/expense totals to avoid double counting.
Savings rate = (income - expenses) / income × 100 when income is greater than zero; otherwise display Not available.
Category totals and monthly trends are calculated.
Charts and summary cards are rendered.
9.7 Budget workflow
User creates a budget for a period (monthly or custom) and assigns category limits.
System calculates actual expense for the selected period and category.
Remaining = budget limit - actual spending.
Percentage used = actual / limit × 100.
When configured thresholds are crossed, create a BudgetAlert and Notification, avoiding duplicate alerts for the same threshold and period.
User can edit, pause or archive a budget.
9.8 Anomaly workflow
AnalysisRun records a new analysis request and selected date range.
System calculates features such as amount relative to category median, recent spending frequency, day/time pattern and merchant history.
Rule-based checks flag clear cases (for example, a transaction far above the user's own historical median).
Optional ML/statistical model assigns an anomaly score.
AnomalyResult stores the score, explanation, related transaction and model/run reference.
User reviews the result and marks it Expected, Incorrect or NeedsFollowUp.
AnomalyReview records the decision and optional explanation.
An anomaly is not proof of fraud. The interface must say 'unusual activity' or 'review suggested', not 'fraud detected'.
9.9 Recurring-payment workflow
Group transactions by merchant/account and similar amounts.
Sort dates and calculate gaps between candidate payments.
Look for repeated intervals (for example, approximately 7, 30 or 365 days) within a tolerance.
Create a SubscriptionDetection candidate with evidence and confidence.
User confirms or rejects the candidate.
Confirmed subscription is stored in Subscription; future matching payments are linked to SubscriptionPayment.
10. Database Design Principles
Use integer primary keys for simple internal identifiers; UUIDs may be used for public-facing identifiers if desired.
Use ForeignKey constraints for all genuine parent-child relationships.
Use Numeric(12,2) for monetary values. Do not use Float for money.
Use Date for transaction dates and DateTime with timezone-aware handling for event timestamps.
Use nullable=False for required fields; use unique constraints for emails and other true unique values.
Use indexes on user_id, account_id, transaction_date, category_id, merchant_id, import_batch_id and common filter combinations.
Use ondelete behavior deliberately (CASCADE only for dependent private child records; RESTRICT/SET NULL where history must remain).
Use check constraints for positive amounts, valid ranges and allowed values where supported.
Store created_at and updated_at consistently. Consider soft deletion for financial records and audit history.
Do not create tables only to inflate the count. Every model below has a defined purpose and relationships.
Create migrations and verify that the actual database contains at least 40 tables after migration.
Implementation note: some lookup/reference tables (Role, AccountType, TransactionType, TransactionStatus) are legitimate relational tables. Seed them with controlled values. The ORM class count alone is not enough: the migrated database must actually contain the tables, and the relationships/CRUD must work.

13. Transaction Categorization and ML Design
13.1 Canonical input
{  "transaction_date": "2026-11-03",  "description_original": "POS PURCHASE KFC DHA",  "amount": "1500.00",  "currency_code": "PKR",  "direction": "expense",  "reference": "optional bank reference"}
13.2 Processing sequence
Preserve the original description exactly as received (subject to safe length limits).
Create normalized text: lowercase, trim, collapse whitespace, standardize common punctuation and remove irrelevant repeated codes only when safe.
Try merchant alias matching. A recognized alias may provide a merchant and default category.
Try user-specific and global category rules in a defined priority order.
If no deterministic match exists, call the ML classifier.
Store predicted category, confidence, method and model version where applicable.
Apply a configurable decision policy: auto-suggest for high confidence, ask confirmation for medium confidence, and mark Uncategorized for low confidence.
Store user confirmation/correction as reviewed feedback. Do not retrain immediately on every single edit; periodically create a validated training set and version a new model.
13.3 Training data
Training data should contain transaction description text and a human-confirmed category label. Do not train on synthetic labels that simply repeat the model's own guesses. A small class-balanced seed dataset can be manually prepared for the demo, then expanded using reviewed corrections.

13.4 Model approach
Baseline: TF-IDF vectorizer over normalized description text + LogisticRegression classifier.
Compare a Multinomial Naive Bayes baseline if useful.
Use a train/test split that avoids putting near-identical examples in both sets where possible.
Evaluate with accuracy, macro F1, per-class precision/recall and confusion matrix; accuracy alone can hide weak minority categories.
Persist the vectorizer and classifier together with a model version and training metadata.
Never silently overwrite user-confirmed categories when a new model version is deployed.
13.5 Confidence and explainability
Use classifier probability only as a confidence estimate, not a guarantee. Calibrate probabilities if the application depends on them. Show a reason such as 'matched merchant alias', 'matched rule: Shell', or 'ML suggestion: Transport (0.78)'. Allow the user to override every suggestion.

17. Forms, Validation, Sessions and Security
17.1 Server-side validation
Validate every submitted field on the server even if HTML required/min/max attributes exist.
Check email format and uniqueness; normalize case/whitespace.
Check amount is finite, positive and within configured limits.
Check transaction date and budget period boundaries.
Check referenced account/category/merchant belongs to the user or is approved global data.
Check uploaded file type, size, columns and row count.
Return field-specific errors and preserve safe form values after validation failure.
Never trust hidden form fields for user_id, ownership, price or role.
17.2 Sessions and cookies
Use Flask's signed session cookie for authenticated session state; do not put financial records or secrets in the cookie.
Set a long random SECRET_KEY in environment variables.
Enable SESSION_COOKIE_HTTPONLY and SESSION_COOKIE_SAMESITE='Lax'; set SESSION_COOKIE_SECURE=True under HTTPS.
Use CSRF protection on all state-changing forms.
Regenerate or clear session state at authentication boundaries as supported by the chosen session implementation.
Do not store passwords, bank credentials, raw reset tokens or API secrets in sessions.
17.3 Security baseline
Use Werkzeug password hashing; never store plaintext passwords.
Use SQLAlchemy parameterized queries; avoid string-built SQL.
Enforce ownership in every object lookup and service method.
Use Jinja autoescaping; do not mark untrusted text as safe HTML.
Protect against CSRF, XSS, SQL injection, path traversal and unsafe file uploads.
Limit login/reset attempts and use generic login error messages to reduce account enumeration.
Use HTTPS in deployment and keep secrets out of source control.
Back up database and private uploads securely; define retention/deletion policy.
Do not collect bank login credentials, card PINs, OTPs or CVVs.

23. Deployment Notes
Use a production WSGI server (for example Gunicorn on Linux or a suitable Windows production server), not Flask's development server.
Use HTTPS and secure cookie settings.
Use MySQL or PostgreSQL for a multi-user production deployment; SQLite is suitable for a small local demo.
Set secrets through hosting environment variables.
Run migrations during deployment in a controlled release step.
Keep uploaded statements, attachments, reports and ML artifacts outside the public static directory.
Restrict file permissions and configure backups.
Add structured error logging that excludes passwords, tokens and unnecessary transaction details.
Set DEBUG=False in production.
Use a background task queue only if imports/reports become too slow for a normal request; it is optional for the university prototype.

Appendix A — Important Implementation Decisions
Bank connection: not required for first release. CSV/XLSX and manual entry are the supported input methods.
Money: use Numeric/Decimal and store currency code. Do not aggregate currencies without conversion.
Transactions: store original description and normalized description separately.
Categorization: merchant match → rules → ML → user review. Uncategorized is a valid result.
ML: train only on reviewed labels; preserve model version and prediction metadata.
Anomalies: alert for review, never claim confirmed fraud.
Privacy: no bank passwords, PINs, OTPs or CVVs.
Database: verify physical table count after migration. If the tag association table is counted separately, ensure the schema still meets the 40-table minimum.
CRUD: provide working Create, Read, Update and Delete/archive paths; lookup tables may have admin-only CRUD.
Documentation: keep README concise for setup; this technical document is the full system blueprint.
